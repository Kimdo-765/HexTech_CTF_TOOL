# 완료 job 검토 → 수정 사항 정리 (2026-08-14)

대상: 최근 완료된 job들 (web 3건, rev 다수) + 앞선 두 보고서의 1·2번 항목.
근거는 모두 job 아티팩트(run.log / result.json / meta.json / events.jsonl)와 코드 라인에서 직접 확인.

**생존 코퍼스 주의**: 현재 `data/jobs`에 남은 job은 15건이며 **전부** `agent_provider=gpt`,
`gpt_runtime=codex`다. Claude 제공자 job은 TTL로 이미 회수되어 비교군이 없다 (→ B1).
아래 결론 중 제공자에 의존하는 것은 그 사실을 명시했다.

## A. 코드 수정 — 안전 (동작 축소 없음)

### A1. codex 하네스가 64 KiB 한 줄에 죽는다  ★최우선 · 실증됨
- **위치**: `modules/codex_cli.py:494` — `asyncio.create_subprocess_exec(...)`에 `limit=` 없음.
  소비 지점 `:532` — `line = await asyncio.wait_for(self._proc.stdout.readline(), remaining)`.
- **원인**: asyncio 스트림 기본 한계 64 KiB. codex가 그보다 긴 JSON 한 줄을 뱉으면
  `readline()`이 `ValueError`를 던지고 세션이 그 자리에서 죽는다.
- **실증** (추정 아님 — 아티팩트에 그대로 있음):

  ```
  data/jobs/a213e7591fdf/result.json:
    "agent_error_type": "ValueError",
    "agent_error": "Separator is not found, and chunk exceed the limit",
    "agent_error_traceback": "... File \"/app/modules/_common.py\", line 8545,
        in run_main_agent_session / async for msg in client.receive_response ..."
  data/jobs/a213e7591fdf/run.log:
    line = await asyncio.wait_for(self._proc.stdout.readline(), remaining)
    ValueError: Separator is not found, and chunk exceed the limit
  ```

  `98a0718483c9`도 **동일한 세 필드가 글자 그대로 동일**하다. 이틀 사이 2회 재발
  (`a213e7591fdf` 4턴 만에 `failed`, `98a0718483c9` 1턴 만에 종료).
- **수정**: `create_subprocess_exec(..., limit=16 * 1024 * 1024)` +
  `readline()`을 `ValueError`에서 죽지 않게 감싸 부분 읽기/스킵으로 폴백
  (한계를 올려도 언젠가는 넘을 수 있으므로 상한 상향만으로 끝내지 않는다).
- **크기/위험**: 한 줄 + 예외 처리. 위험 낮음.
- **회귀 테스트**: 64 KiB 초과 한 줄을 뱉는 가짜 프로세스로 `ValueError` 미발생 확인.

### A2. prejudge가 막는 동안 샌드박스를 한 번도 안 돌리고 ~$717을 태운다  ★최우선
- **위치**: 차단 판정 `modules/_runner.py:1243` (`prejudge_blocks_ship` → "sandbox NOT spawned"),
  리다이렉트/상한 루프 `modules/_common.py:9616~9709` (`_n < 3` → BLOCKED 4회까지 진행).
- **측정값** (web 3건, 세 건 전부 수치가 동일):

  | job | 턴 | 추정 비용 | BLOCKED | redirect | cap-stop | concede | 샌드박스 |
  |---|---|---|---|---|---|---|---|
  | `e34c4b63b50b` | 373 | $132.95 | 4 | 3 | 1 | 0 | 0회 |
  | `f3a67cd86353` | 406 | $252.28 | 4 | 3 | 1 | 0 | 0회 |
  | `eb18a95f4399` | 293 | $332.43 | 4 | 3 | 1 | 0 | 0회 |
  | **합계** | **1072** | **~$717.66** | | | | | **0회** |

  ("샌드박스 0회"는 `_runner.py:1243`의 차단 경로가 spawn 이전에 return하기 때문 — 로그 문구 자체가
  "sandbox NOT spawned"다.)
- **원인 구조**: `flag_likelihood`가 0.02~0.08로 낮아 매번 severity=high → ship 차단.
  차단은 리다이렉트로 3회까지 되돌려지고 4번째에야 멈춘다.
  concede 게이트(`_common.py:9658`)는 **self-defeat 이슈**를 요구하는데 web은 그걸 내지 않으므로
  발동하지 않는다(실측 concede=0).
- **수정**: 상한을 낮추는 게 아니라 **조기 에스컬레이션**을 넣는다 —
  "BLOCKED 2회 연속 + 샌드박스 실행 0회"면 자동 재시도를 멈추고 운영자에게 넘긴다.
  누적 턴/추정 비용을 stop 사유에 함께 기록.
- **구현 순서 지정 (중요)**: 새 에스컬레이션은 concede 게이트와 **같은 `_n` 값에서 만난다**
  (concede는 `_n >= 1`, 즉 두 번째 차단에서 발동). 반드시
  **concede 게이트를 먼저 평가하고, 그 다음에 에스컬레이션**을 둔다.
  순서가 뒤집히면 356b8d0이 일부러 넣은 `unsolvable_by_analysis` stop_kind가 영원히 안 나온다.
- **명시적 가정 (미검증)**: `_common.py:9634` 주석은 `6b8b78b702b1` / `824412f1ada49`가
  리다이렉트로 구제됐다고 적고 있으나, 두 job 모두 **이미 TTL로 회수되어 run.log가 없다**.
  따라서 "몇 번째 리다이렉트에서 구제됐는가"는 확인 불가다. 2회에서 끊으면 리다이렉트 1회만 남으므로,
  그 job들이 2·3회차에서 구제된 것이었다면 회귀다. **이 가정을 감수하고 진행하거나,
  에스컬레이션을 3회로 잡아 리다이렉트 2회를 남기는 선택**이 있다. (→ 이런 확인 불가 자체가 B1의 사례)
- **크기/위험**: `_common.py` 한 블록. 멈추는 방향이라 새 비용을 만들지 않음.
  단, A3 없이는 멈춘 이유가 로그에 안 보이므로 **A3와 함께 나가야 한다.**

### A3. WHY_STOPPED가 서로 다른 두 상황을 똑같이 "verdict: unknown"으로 적는다
- **위치**: `modules/_common.py:6915`(파일명 상수), `:6921`(`"no_hint"` 문구),
  작성부 `:7184` / `:7233`, 분기 `:7376`; verdict 기본값 `modules/_runner.py:1405`.
- **증상**: ① prejudge가 N회 막아 샌드박스가 아예 안 돈 경우와
  ② judge가 shadow 모드라 enforce 판정이 없는 경우가 둘 다
  "Postjudge verdict: unknown"으로 적힌다. 운영자가 로그를 파헤치기 전에는 A2를 볼 수 없다
  (이번에도 내 첫 보고서가 이걸 "judge 파싱 실패"로 오진했다).
- **수정**: stop_kind 분리 —
  `prejudge_blocked_no_run`(차단 횟수·샌드박스 0회·누적 비용 명시),
  `judge_shadow_no_verdict`(판정이 아무것도 게이트하지 않음을 명시). 기존 `no_hint`는 유지.
- **크기/위험**: 문구 + 분기. 위험 낮음.

### A4. 집계기가 진행 중 job과 `stopped_for_resume`에서 예외로 죽는다
- **위치**: `scripts/aggregate_hardening.py:824`
  (`AggregationError: unresolved failure classification: 2b495752ce97, c09f2a6c48ff`).
- **증상**: 진행 중(`running`)이거나 재개 대기(`stopped`)인 job이 하나라도 있으면 집계 전체가 실패.
  베이스라인을 다시 돌릴 때마다 손으로 제외해야 한다.
  현재 코퍼스에도 `2b495752ce97`(running), `c09f2a6c48ff`/`d5e018600139`(stopped)가 있다.
- **수정**: 두 상태를 사유 태그와 함께 `excluded`로 분류. 그 밖의 미분류는 지금처럼 예외 유지
  (조용한 오분류보다 시끄러운 실패가 낫다는 기존 설계를 지킨다).
- **크기/위험**: 분류 함수 한 곳 + 테스트 2개. 위험 낮음.

### A5. 사용량 표시가 codex job의 지출을 $0으로 센다  ※ 진단 정정됨
- **최초 진단이 틀렸다**: `_common.py:3982`의 `"cost_usd": float(cost_usd or 0.0)`는
  **서브에이전트 응답 캐시 항목**이지 `meta.cost_usd` 기록부가 아니다. 무관하다.
- **실제 원인**: `modules/codex_cli.py:758` — `total_cost_usd=None` 하드코딩.
  ChatGPT 구독은 호출 단위로 과금하지 않으므로 codex는 권위 비용을 **원래 안 준다**
  (`modules/usage_ledger.py:15`가 같은 이유를 명시). 즉 이건 codex 쪽의 버그가 아니다.
- **실제 결함은 소비처**: `api/routes/jobs.py:_job_cost()` (`:81`)는 `meta.cost_usd`만 읽고,
  `get_stats()` (`:357` `bucket["cost_usd"] += cost`)가 그걸 합산하며,
  종료된 job이 cost 0이면 `:351`의 `elif cost == 0.0: pass`로 **명시적으로 장부에서 뺀다**.
  그 합계가 `/usage`의 `spent_usd`(`:386`)이고 `budget_usd` 대비 잔액 계산의 분자다.
  → 현재 15건 전부 `cost_usd`가 `0.0`/`None`인데 `cost_usd_estimate` 합계는 **약 $803.10**.
  운영자 예산 표시는 $0을 가리킨다.
- **수정**: 종료된 job에 권위 비용이 없으면 `cost_usd_estimate`로 폴백하되,
  응답에서 **추정치임을 분리해 표시**한다(예: `spent_usd` / `spent_estimated_usd`).
  `meta.cost_usd`를 `null`로 바꾸는 건 불필요 — `_job_cost`가 이미 `or 0.0`으로 정규화한다.
- **주의 소비처**: `modules/_common.py:8410`의 `_maybe_cost_cap()`은 meta가 아니라
  `summary["cost_usd"]` + `summary["result"]["total_cost_usd"]`(`:8396~8401`)를 읽는다.
  **이 캡은 건드리지 말 것** — 여기 손대면 안전 게이트가 바뀐다.
- **크기/위험**: `api/routes/jobs.py` 국소 수정. 캡을 안 건드리면 위험 낮음.

### A6. flag 후보 추출에 노이즈가 섞인다  ※ 범위 축소됨
- **증상**: 후보 목록에 `DH{[^}`(정규식 조각)가 올라온다.
- **수정**: **닫는 `}`가 없는 후보만** 제외한다. `DH{[^}`가 정확히 여기 걸리고,
  진짜 flag는 정의상 닫혀 있으므로 걸릴 수 없다.
- **하지 말 것**: "정규식 메타문자 포함 후보 제외"(최초안). 진짜 flag에는 `?`, `.`, `$`, `+`,
  `*`, `(`, `|`가 흔히 들어간다 — a3d4d448에서 폭 휴리스틱이 진짜 `DH{<64hex>}`를 버린 것과 같은 모양이다.
- **하지 말 것**: 플레이스홀더(`DH{real_flag-123}`) 자동 폐기. 운영자 방침상
  flag 큐레이션은 수동(🗑️/📌)이다.
- **크기/위험**: 필터 한 줄. 위험 낮음.

### B1. `job_ttl_days=7`이 측정 코퍼스를 파괴한다
- **위치**: `modules/settings_io.py:52` — `("job_ttl_days","JOB_TTL_DAYS",int,7)`.
- **증상**: S1 베이스라인 20건 중 **0건 생존**. 개선 전후의 분류 분포 비교가 설계상 불가능하다.
  이번 조사에서도 실제로 두 번 막혔다 — A2의 리다이렉트-구제 job 2건을 확인할 수 없었고,
  Claude 제공자 job이 전멸해 A5의 제공자 상관을 대조군 없이 판단해야 했다.
- **선택지**: (a) TTL을 30일로 올린다, (b) TTL은 두되 회수 전에
  `events.jsonl` / `meta.json` / `run.log`만 별도 보관 디렉터리로 승격한다.
- **권고**: (b). 디스크를 지키면서 측정 입력(append-only·타임스탬프)만 남긴다.
- **결정 필요**: TTL 값 또는 보관 정책은 운영자 판단.

## C. 운영자 결정 필요 — 게이트 정책 변경

### C1. `flag_likelihood < 0.2` 하드컷 완화 (앞선 보고서의 3번)
- **위치**: 정책 근거 주석 `modules/_runner.py:1193` (Tier 1.7), 판정 `_judge.prejudge_blocks_ship()`.
- **쟁점**: 이 컷은 실제로 낭비를 막은 이력이 있다 (`7f903a8e152b`: fl=0.02에서 사이클 낭비).
  반대로 web 3건은 이 컷 때문에 샌드박스를 **한 번도** 못 돌려 봤다.
  또 과거 concede 판정이 틀렸던 전례가 있다 (securalloc — 실제로는 풀 수 있었다).
- **정리**: A2(조기 에스컬레이션)만 넣어도 $717짜리 출혈은 멈춘다.
  컷 자체를 건드리는 건 별개 결정이므로 **승인 없이는 구현하지 않는다.**
- **선택지**: (a) 현행 유지 + A2만 적용 **(권고)**, (b) web 모듈만 컷을 0.1로 완화,
  (c) 컷을 "차단"이 아니라 "1회 실행 허용 후 재평가"로 바꾼다.
